# Retro — the 14-hour push, 2026-07-17

*What we learned, not what we did. Sources: git history across ssi-learning-app, this repo, and
zenjin-2026-v1; docs/trinity/* in both apps; the Zenjin audit (`zenjin-2026-v1
docs/audit-2026-07-17.md` on `claude/zenjin-audit`); CoS memory written during the session.*

---

## 1. What actually broke and why

An overnight agent, correctly following the grant-hygiene doctrine, applied it to the wrong
table: a direct-psql `REVOKE` — no migration, no canary — stripped authenticated access from
`player_events`. The doctrine exists for org tables that clients should never touch;
`player_events` is the one table an authenticated client legitimately reads (the admin per-user
diagnostic path). Result: 403s for signed-in learners, admin panel and demo links dead in the
middle of a customer demo. Fixed live by hand, then backfilled as migration
`20260717_restore_player_events_authenticated_grant.sql`.

Three generalisable lessons, in order of weight:

1. **State that only ever existed as a live psql command is invisible to every instrument we
   have.** Git diff, PR review, worker audits, the schema snapshot — all green while prod was
   broken. The change had no artefact, so nothing could catch it, question it, or revert it. The
   defect wasn't the REVOKE; it was the channel.
2. **A doctrine without a scope test misfires exactly where it's most confidently applied.** The
   agent wasn't being sloppy — it was being diligent with a rule that didn't say where it stops.
   Every "always do X" rule we write needs its boundary written next to it.
3. **The architecture saved what the process broke.** Learner writes never failed, because
   they're server-mediated through the service role. Client-direct DB access was the only
   casualty. That asymmetry is the strongest argument we've ever produced for server-mediated
   everything.

## 2. Recurring process failures (happened more than once)

1. **Ad-hoc DB mutations via live psql.** Twice in one night: the REVOKE above, and the
   adaptation-v2 config row seeded "applied live via psql" during the re-soak setup (that one at
   least re-snapshotted the schema). Fix adopted: grants/RLS/config changes go through committed
   migrations only — see doctrine delta 1.
2. **Workers stalling, parked on a deploy or external state.** A worker waiting is a worker
   burning window doing nothing, invisibly. Fix to adopt: workers never wait — they finish with
   a handoff note saying what they're blocked on; the orchestrator owns all waiting and
   re-dispatches when the state changes.
3. **Workers ending mid-task with no report.** The cardinal sin — "I'll handle it" then silence.
   Fix adopted in-session: killed/stalled work goes on a re-dispatch list, nothing is presumed
   done without a report; every dispatch must end in a report, a failure notice, or an
   interruption notice.
4. **The 5h-window token trap.** The binding constraint is the 5-hour session bucket, not the
   weekly allowance — a ~50-worker burst emptied the session in ~15 minutes with ~70% of the
   week's tokens untouched, then spilled into credit overage at ~£50 in 10 minutes. Fix adopted:
   overage off; meter ~a dozen workers staggered across the window; the moment spend-limit
   errors appear, stop dispatching — firing into the cap is pure waste.
5. **REPORTED findings flipping false on contact with real code.** Around five audit claims
   didn't survive verification; in the Zenjin audit one worker finding changed shape entirely on
   lead re-verification (a "duplicate pair on screen" that was actually a two-rung flat-spot),
   and two findings were lost in worker→lead relay. Separately, the adaptation persistence bug's
   first reported cause (RLS/missing migration) was wrong — the real cause was a captured ref
   frozen pre-auth. Fix adopted: the Zenjin method — every load-bearing worker claim re-verified
   by execution or direct source read before it enters the ranked ledger; anything unverified is
   marked as such. See doctrine delta 5.

## 3. What worked — institutionalise these

- **Verify-before-trust, by execution.** The Zenjin audit drove the real `Session` class with
  persona answer-providers, no mocks — claims proven by running code, not by reading it. That's
  why its findings held. Same energy from workers that refused wrong instructions and corrected
  the brief instead of silently complying: a worker that pushes back is worth ten that comply.
- **The verified/reported split, marked in the ledger.** Cheap to write, and it's the only thing
  that stops a plausible-but-wrong finding becoming a plausible-but-wrong fix.
- **Metered fleets over bursts.** A dozen workers staggered across the window did the same work
  as the 50-agent burst without touching credit. Fleet cadence is the lever, not start time.
- **Server-mediated over client-direct DB.** Proven under live fire (section 1), and extended
  the same day: account self-delete, reset-progress, and hierarchy deletes all moved
  server-side. Direction of travel: the client talks to our API; only our API talks to the DB.
- **The Trinity method scales.** Every screen decomposed into typed messages (App→User,
  User→App, App→App), each validated, findings classed 1–5. The missing-twin class alone — an
  App→App process with no App→User failure message — is the bug class behind the paywall
  dead-tap and the silent metrics writes. Both apps are now message-mapped in docs/trinity/*.
- **Durable-truth telemetry.** Position as the durable record, logged time as primary — state
  the learner's truth from what was actually played, not from inferred session bookkeeping.
- **Degradation-ladder-first design.** 90% for all lang-pairs beats 100% for a handful. Design
  the fallback ladder before the feature: missing asset → nearest coarser asset → visible
  pending state, never a silent dead control. Speed has a quality all its own.

## 4. Doctrine deltas — standing policy from today

1. **Grants, RLS, and DB config change only via committed migration, applied with a canary
   check — never direct psql.** A live-psql fix under fire is a stopgap that must be backfilled
   as a migration the same day, or it didn't happen.
2. **Size fleets to the 5h session window, not the weekly balance.** Meter big campaigns —
   roughly a dozen workers staggered, not fifty at once. Spend-limit errors mean stop
   dispatching immediately. Credit overage stays off.
3. **Keep a standing backlog of expensive Fable jobs.** The weekly allowance goes unused if work
   only happens in bursts; a live queue of genuinely valuable Fable-tier jobs (deep audits,
   synthesis, texture passes) gets metered into every window so capacity is never left on the
   table. The bar for the queue: would Tom value the artefact.
4. **Every App→App message ships with an App→User failure twin.** A process the user can't see
   fail is a defect, full stop — Trinity finding class 3. Audits hunt for it; new code doesn't
   ship without it.
5. **VERIFIED vs REPORTED is marked and reported honestly, everywhere.** Nothing unverified
   enters a ranked ledger or a status report as fact. Worker claims are re-verified by execution
   before ranking; relay loss is real, so the lead owns the reconciliation.
