# A-112: S3 versioning on the audio bucket

**2026-08-16.** Scope, per Tom's ruling: enable S3 object versioning on the audio bucket, prove
it's on, and manage the noncurrent-version cost tail. Nothing else — no Supabase PITR, no extra
DB backup job, no Watson/command-surface backup (all explicitly rejected by Tom the same
afternoon).

## Which bucket

The audio bucket is `ssi-audio-stage` (`S3_BUCKET` / `S3_AUDIO_BUCKET` in the repo root `.env`,
region `eu-west-1`), referenced ~2,359 times across the repo. The two other names that turned up
in a repo-wide grep — `ssi-audio-cache-v2` and `ssi-audio-v1` — are **not S3 buckets at all**:
they're browser-side IndexedDB store names used by the PWA offline cache (`AudioCache`,
`packages/player-vue/src/cache/AudioCache.ts`). There is no second S3 bucket in scope.

## Before state

- `GetBucketVersioning` on `ssi-audio-stage`: **`Status: "Enabled"`** — already on before this
  session touched anything. A repo-history grep for prior S3-versioning work turned up nothing
  obviously responsible; who/when isn't established. Reported plainly rather than silently

- `GetBucketLifecycleConfiguration`: `NoSuchLifecycleConfiguration` — no lifecycle configuration
  existed.

## What was done

1. **Versioning**: `PutBucketVersioning { Status: "Enabled" }` sent (a no-op given the before
   state, but run as specified). Confirmed via a fresh `GetBucketVersioning` immediately after:
   `Status: "Enabled"`.
2. **Functional proof** (not just an API echo): wrote a throwaway object twice under
   `_versioning-probe/a112-<timestamp>.txt` with different content on each PUT, then called
   `ListObjectVersions` for that key. Two distinct version IDs came back for the same key:
   - `VEykrD19pKVtWzG7j_kU6aEnVhRnL7Uy` (first write, became noncurrent)
   - `0P4MNupRqSWzLUWpcDntqS8qFmWOKMWe` (second write, was latest)

   Both versions were then deleted explicitly by version ID (a plain delete on a versioned bucket
   only writes a delete marker — that would have left the marker behind). A follow-up
   `ListObjectVersions` on the same prefix confirmed zero objects/markers remain. No non-probe
   object was touched.
3. **Lifecycle**: since no configuration existed, one rule was applied —
   `NoncurrentVersionExpiration.NoncurrentDays: 90`, plus `AbortIncompleteMultipartUpload` after 7
   days. **90 days is a default this session picked, not a number Tom gave** — comfortably longer
   than Supabase's 7-day daily-backup window, so a mistake found weeks later is still recoverable,
   while bounding the storage tail. One-line change (`NoncurrentDays`) if Tom wants it longer or
   shorter. The rule only ever touches **noncurrent** versions — current object versions are
   never expired, transitioned, or deleted by it.

## What this changes operationally

- **Versioning is not reversible in the ordinary sense.** Once enabled, a bucket can only move to
  `Suspended`, never back to "never versioned".
- **Versioning is not retroactive in the way it might sound, but it does cover overwrites.** It
  protects objects from the moment it's on, going forward — but because an overwrite of an
  existing key *creates a new version*, the bytes that were current at enable-time become the
  noncurrent version the first time anything overwrites them. So an accidental overwrite or
  delete from now on is recoverable; it isn't a snapshot of today's state taken today.
- **A delete now leaves a delete marker, not removed bytes.** `DeleteObject` without a
  `VersionId` writes a delete marker; the prior version(s) are still in the bucket and readable via
  `ListObjectVersions` / `GetObject` with an explicit `VersionId`.
- **Recovering a clobbered clip**: `ListObjectVersions` on the key to find the wanted `VersionId`,
  then copy that version over the current key (`CopyObject` with `CopySource` including the
  version ID, or `PutObject` with the fetched bytes). This is the safety net behind the
  make-before-break doctrine — see the pointer added to
  `docs/architecture/AUDIO_PIPELINE_ARCHITECTURE.md` §6b.
- **Cost tail**: noncurrent versions now accumulate for 90 days before expiring, so overwrite/regen
  churn adds some ongoing storage cost. **Explicit gap: this session could not get a bucket-size
  figure cheaply** — `@aws-sdk/client-cloudwatch` isn't installed in this checkout and `aws` CLI
  isn't available, and a full `ListObjectsV2` walk of a bucket this large wasn't a good use of the
  minutes this job was scoped for. No rough £/month figure is given; that's a real gap, not a
  guess dressed up as one.
