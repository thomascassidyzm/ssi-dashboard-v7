## P2 — Backend settings are not attached to the reads in transaction pooling

- **Location:** `tools/qa/lib/name-backend.cjs:19-20`.
- **Failing configuration and input:** a transaction-pooled Supavisor connection with two available server backends; call `nameBackend(client, 'qa:audio-gap', { statementTimeoutMs: 900000 })`, then run the caller's course query and audio-gap aggregates. Each `client.query` here is a separate implicit transaction. The pool can execute the name setter on backend A, the timeout setter on backend B, and the aggregate on A or another backend. There is no guarantee that the aggregate has both the requested name and timeout. It can still hit the original backend timeout and produce no nightly snapshot. Ending the Node connection does not establish that these session settings belonged exclusively to that check.
- **Evidence in this checkout:** all four changed callers invoke this helper outside an explicit transaction. The existing `tools/qa/voice-variety/named-read.cjs:31-43` explicitly supports both session and transaction pooling by enclosing the settings and reads in `BEGIN READ ONLY` / `COMMIT` and using transaction-local settings. Its adjacent tests document why backend settings must be set inside the transaction containing the reads. The new helper omits that protection.
- **Smallest fix:** use the existing `namedRead` pattern around each caller's database work, with the required per-check timeout; set name and timeout locally inside that transaction. Adding `BEGIN` and `COMMIT` around only this helper would not fix it: the reads must share the transaction.
