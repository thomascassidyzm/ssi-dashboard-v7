## 1. [P1] A failed background pod-index refresh produces an unhandled rejection

**Location:** `services/pod-search-router.cjs:191–193`.

**Concrete failing input:** First populate the index with an authenticated `GET /api/pod-search?q=hello`. After its ten-minute TTL, send the same request while any index query fails, for example a PostgREST timeout reading `listening_pods`.

**Proof:** `build()` at lines 168–177 awaits `readAllPages`; `services/shared/paged-read.cjs:26` throws on a returned query error. `getIndex()` attaches only `.then(...).finally(...)` to that build at line 191, then returns `current` at line 193. The request's `await getIndex(...)` at line 208 therefore resolves successfully with the stale index; its catch cannot receive the detached refresh's rejection. No rejection handler is attached to the promise returned by `finally`. The scenes route uses the same `getIndex` at line 225. This creates an unhandled rejection on a routine database failure. Under Node's default unhandled-rejection policy that terminates the Production API; the committed system unit starts `/usr/bin/node services/production-api.cjs` without a policy override (`ops/systemd/popty-user/popty-production-api.service:28–32`). The router is mounted in that API at `services/production-api.cjs:581–588`.

**Smallest fix:** In the stale-return branch attach a rejection handler to `building` which logs the refresh failure, while leaving the original promise available for first-load and explicit-refresh callers to await and catch. Keep the existing `finally` reset so a subsequent request can retry. Process termination has not been reproduced; the detached rejection follows directly from the promise ownership above.

## 2. [P2] Re-recording can delete the only durable take before its replacement is saved

**Location:** `src/services/autocueTakeShelf.js:58–60` (replacement is written at line 78).

**Concrete failing input:** The shelf contains an unsent take with `courseCode: 'fry_for_eng'`, `voiceId: 'auke'`, and metadata `{ itemId: 'S0001L01', itemKind: 'lego', cadence: 'natural', text: 'hello' }`. Record that same line again with a larger Blob while IndexedDB cannot store the replacement, for example because of `QuotaExceededError`. Its upload also fails during an API outage, and the tab closes.

**Proof:** `createAutocueShelf().put()` finds the matching line/course/voice and awaits deletion of the old record at line 60 before constructing and writing the new record at lines 63–78. These are separate committed transactions: `src/services/takeStore.js:321–345` implements each backend `put` and `remove` with a separate `tx(..., 'readwrite', ...)`. If the new write rejects, the old deletion remains committed. `src/components/production/autocue/AutocueStudio.vue:1102–1115` catches that error, logs it and queues the new take without a `shelfId`. Once that in-memory upload fails and the tab closes, neither take exists on the shelf for `recoverOrphans` to recover. Even a tab crash between the two transactions loses the old durable take.

**Smallest fix:** Collect the superseded ids, persist the replacement first, and remove the old ids only after that write commits. An atomic backend replacement transaction would also work. A failed replacement must leave the earlier take recoverable. Storage failure and browser closure were not induced; the deletion/write ordering and caller's fallback are verified in code.

## 3. [P2] Explicitly clearing a phrase's romanisation silently restores the existing value

**Location:** `services/shared/roman-sync.cjs:64–66`.

**Concrete failing input:** `withExplicitRoman({ target_text: '你好', target_text_roman: null }, { target_text: '你好', target_text_roman: 'incorrect old reading' })`. This returns `target_text_roman: 'incorrect old reading'` instead of `null`. The same failure occurs with an explicitly empty string.

**Proof:** `nonEmpty(null)` produces null at line 64; because the target characters are unchanged, line 65 selects the old romanisation, and `sent || kept` restores it at line 66. This is reached by `POST /api/v2/phrases/:courseCode` (`services/course-builder/routes/v2.cjs:767`): the BUILD and USE row builders pass through `p.target_text_roman` at lines 936 and 964; lines 988–994 read the existing row at that position and call this helper; lines 998–1000 upsert the result. Thus a valid phrase-set resubmission with unchanged target characters and an explicit null cannot remove a wrong reading. The helper's own contract at lines 55–57 gives precedence to what the caller sent, and `romanGoesStale` at lines 33–34 likewise treats an explicitly supplied romanisation field as intentional.

**Smallest fix:** Distinguish `row.target_text_roman !== undefined` from omission: if defined, return its normalised value even when null; only preserve the existing reading when it was omitted and the target text matches. The v2 row builders always create the property, including with undefined, so testing property presence alone would wrongly clear omitted values. No route call or database write was made.
